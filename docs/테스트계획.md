# 페르소나 테스트 계획

## 왜 이렇게 하나

기능이 다 붙었는지 확인하는 것과, **쓸 만한지** 확인하는 것은 다른 일입니다.
지금 자동 테스트 160개는 "코드가 의도대로 도나"를 봅니다. 여기서는
**사람이 이 화면을 실제로 쓸 때 어디서 막히나**를 봅니다.

방법은 두 가지를 겹쳐 씁니다.

**1) 세션 기반 탐색 테스트 (SBTM)** — James·Jon Bach가 정리한 방식입니다.
정해진 절차서를 따라가는 대신 **미션(charter)** 을 정해 시간을 끊어 훑고,
끝나면 세션 시트에 발견을 적습니다.
([Session-based testing](https://en.wikipedia.org/wiki/Session-based_testing))

**2) 페르소나 charter** — 미션을 "누가, 어떤 기기로, 어떤 상황에서"까지
적어 실제 사용자 행동을 흉내 냅니다. 절차를 정해주지 않아 **정해진 길 밖의
문제**가 걸립니다.
([Persona-Based Testing](https://www.testriq.com/blog/post/persona-based-testing-enhancing-qa-with-real-user-simulation),
[Test charters](https://www.getxray.app/blog/test-charters-exploratory-testing))

빠뜨리는 축이 없도록 커버리지는 **SFDIPOT**(Structure·Function·Data·
Interfaces·Platform·Operations·Time)로 점검했습니다. James Bach의 휴리스틱
테스트 전략 모델에 있는 목록입니다.
([HTSM](https://rapid-software-testing.com/heuristic-test-strategy-model/),
[SFDIPOT](https://www.sharonob.com/blog/sfdipot))

## 2회차 — 1회차에서 안 밟은 축

1회차는 사람이 화면을 쓰는 흐름 위주였습니다. SFDIPOT 로 다시 훑어 보니
**Interfaces(연동) · Data(경계값) · Time/Operations(동시성·되돌아가기) · Structure(없는 주소)**
가 비어 있어 다섯 명을 더 만들었습니다.

| # | 누구 | 기기·상황 | 미션 | SFDIPOT |
|---|---|---|---|---|
| P9 | **A사이트에서 넘어온 회원** | `AUTH_MODE=host` · 서명 토큰 | 자체 가입이 닫혔나, 토큰으로 들어와 글까지 쓰나, 위조·만료 토큰은 막히나 | Interfaces |
| P10 | **개복치** 경계를 밟는 사람 | 데스크톱 | 닉네임 11자, 비번 5자, 제목 50/51자, 본문 5,200자, 빈 제목, 이모지, `%`·`' OR 1=1` 검색 | Data |
| P11 | **산만한 사람** | 탭 두 개 | 출석을 두 탭에서 동시에, 추천 연타, 뒤로/앞으로 재전송, 로그아웃 뒤 열어둔 폼 제출 | Time · Operations |
| P12 | **알림 기다리는 사람** | 두 사람 동시 접속 | 한쪽이 댓글 달면 다른 쪽 종이 저절로 바뀌나 | Interfaces · Time |
| P13 | **길 잃은 사람** | 데스크톱 | 없는 글·회원·쪽번호, 이상한 정렬값, 지워진 글에 댓글, 숨긴 글 열람 | Structure |


## 무엇을 발견이라고 볼까

- **막힘(BLOCK)** — 하려던 것을 끝내지 못함
- **버그(BUG)** — 잘못 동작하거나 잘못 보임
- **거슬림(NIT)** — 되긴 하는데 불편하거나 어색함
- **물음(ASK)** — 기획 결정이 필요해 고칠 수 없는 것

## 어떻게 돌리나

```
node scripts/persona-test.js          # 전부
node scripts/persona-test.js P1 P6    # 골라서
```

- 데모 DB를 **복사해서** 씁니다. 실제 데이터는 건드리지 않습니다.
- 발견은 던지지 않고 모읍니다. 하나 실패해도 끝까지 갑니다.
- 화면은 `docs/persona/` 에 증거로 남습니다.
- 결과는 `docs/페르소나테스트.md` 로 나옵니다.

## 3회차 — 자동 검사가 못 잡던 것 (테두리 사건)

테두리(고리)가 얼굴을 가로질러 그려지고 있었는데, 페르소나 13명이 **발견 0건**으로
통과했습니다. 배포까지 나가서 사람이 눈으로 보고 지적했습니다. 왜 못 잡았는지:

| | 왜 못 봤나 |
|---|---|
| 단위 테스트 | "고리 태그가 있는가"만 확인 — **크기**는 안 봤다 |
| 흐름 테스트 | 화면은 200 OK, 요소도 제자리. 아무 문제 없음 |
| 대비 검사 | 글자 색만 잰다. 그림끼리 겹치는 건 대상이 아니다 |
| 스크린샷 | **남기기만 하고 아무도 안 열어봤다.** 게다가 그림이 뜨기 전에 찍혀 아바타 자리가 빈 동그라미였다 |

원인도 흔한 종류였습니다. `style.css` 의 `.avatar-ring { width: 132% }` 가
위쪽 `.avatar img { width: 100% }` 에게 **우선순위에서 져서** 통째로 무시됐습니다.
문법 오류가 아니라 조용히 무시되는 종류라 어디에도 흔적이 남지 않습니다.

그래서 세 가지를 넣었습니다.

1. **크기를 CSS 에서 뺐습니다.** 고리·얼굴 크기는 `src/avatars.js` 가 요소에 직접
   붙입니다. 인라인 스타일은 어떤 선택자도 이기지 못해 같은 사고가 다시 안 납니다.
2. **눈으로 보던 것을 숫자로 바꿨습니다.** `test/avatar-ring.test.js` 가 테두리 PNG 9장을
   직접 읽어 구멍 크기를 재고, `구멍 ≥ 얼굴` 인지 확인합니다.
   옛 코드로 되돌려 돌려보면 `구멍이 0.61 인데 얼굴이 1 라 19.5% 씩 겹친다` 로 잡힙니다.
3. **스크린샷이 진실을 담게 했습니다.** 찍기 전에 그림이 다 뜰 때까지 기다리고,
   찍을 때마다 *잘라내는 상자 밖으로 삐져나간 그림*이 있는지 함께 검사합니다.

### 남는 한계 (정직하게)

이 셋으로도 **"되긴 하는데 못생겼다"** 는 못 잡습니다. 간격이 어색하다, 색이 진하다,
글씨가 크다 — 전부 이번에 같이 받은 지적인데 기계가 판정할 수 있는 종류가 아닙니다.
이런 건 **사람이 보거나**, 이전 화면과 비교(visual regression)해서 *달라진 곳*을
사람에게 보여주는 수밖에 없습니다. 지금은 전자로 갑니다.

## 4회차 — 사람 눈으로 화면 훑기

3회차에서 "보기 싫은 것은 사람이 봐야 합니다" 라고 적어 놓고, 실제로 화면을
하나씩 열어 봤습니다. 자동 검사 189개와 페르소나 13명이 전부 통과한 상태에서
**5건**이 나왔습니다.

| 화면 | 무엇이 | 왜 자동 검사가 못 봤나 |
|---|---|---|
| 이벤트·포인트 | 구매 내역이 `+-20,000P` (부호 두 개) | 화면에 글자가 있는지만 봤지 *내용*을 안 봤다 |
| 이벤트·포인트 | "오늘 적립 −21,990P" — 적립인데 음수 | 계산은 맞았다. 라벨과 안 맞는 게 문제였다 |
| 캐릭터 상점 | 테두리 칸에서 '사용 안 함'만 얼굴이 큼 (68px 대 55px) | 둘 다 정상 크기다. 나란히 놓였을 때만 어긋난다 |
| 글 상세 | 댓글 입력 안내가 "…하루 10개까" 에서 잘림 | 글자는 다 있다. 칸보다 길 뿐이다 |
| 마이페이지 | "출석 0일" 인데 포인트 내역엔 출석체크·연속 출석 보너스 | 데모 데이터끼리 앞뒤가 안 맞은 것 |

다섯 건 모두 **한 화면 안에서는 아무 문제가 없고, 다른 것과 나란히 놓고 봐야만
드러나는** 종류입니다. 요소 하나씩 검사하는 방식으로는 원리상 안 걸립니다.

고친 뒤에는 다시 숫자로 바꿔 회귀 검사를 붙였습니다
(부호 2개 · 오늘 적립 1개 · 얼굴 크기 1개).

### 이번에 확인해 보고 '결함 아님' 으로 넘긴 것

- 에디터 툴바가 좁은 화면에서 잘리는 것 — 오른쪽에 흐림 처리로 "더 있다" 를 이미 알리고 있었다
- 캐릭터 25칸에서 보유/잠금이 구분 안 되는 것처럼 보인 것 — 보유한 칸이 스크롤 아래에 있었을 뿐
- 알림 카드가 커 보인 것 — 알림이 한 건뿐이라 그렇게 보였다
