# 페르소나 테스트 계획

## 왜 이렇게 하나

기능이 다 붙었는지 확인하는 것과, **쓸 만한지** 확인하는 것은 다른 일입니다.
지금 자동 테스트 160개는 "코드가 의도대로 도나"를 봅니다. 여기서는
**사람이 이 화면을 실제로 쓸 때 어디서 막히나**를 봅니다.

방법은 두 가지를 겹쳐 씁니다.

**1) 세션 기반 탐색 테스트 (SBTM)** — James·Jon Bach가 정리한 방식입니다.
정해진 절차서를 따라가는 대신 **미션(charter)** 을 정해 시간을 끊어 훑고,
끝나면 세션 시트에 발견을 적습니다.
([Session-based testing](https://en.wikipedia.org/wiki/Session-based_testing))

**2) 페르소나 charter** — 미션을 "누가, 어떤 기기로, 어떤 상황에서"까지
적어 실제 사용자 행동을 흉내 냅니다. 절차를 정해주지 않아 **정해진 길 밖의
문제**가 걸립니다.
([Persona-Based Testing](https://www.testriq.com/blog/post/persona-based-testing-enhancing-qa-with-real-user-simulation),
[Test charters](https://www.getxray.app/blog/test-charters-exploratory-testing))

빠뜨리는 축이 없도록 커버리지는 **SFDIPOT**(Structure·Function·Data·
Interfaces·Platform·Operations·Time)로 점검했습니다. James Bach의 휴리스틱
테스트 전략 모델에 있는 목록입니다.
([HTSM](https://rapid-software-testing.com/heuristic-test-strategy-model/),
[SFDIPOT](https://www.sharonob.com/blog/sfdipot))

## 무엇을 발견이라고 볼까

- **막힘(BLOCK)** — 하려던 것을 끝내지 못함
- **버그(BUG)** — 잘못 동작하거나 잘못 보임
- **거슬림(NIT)** — 되긴 하는데 불편하거나 어색함
- **물음(ASK)** — 기획 결정이 필요해 고칠 수 없는 것

## 어떻게 돌리나

```
node scripts/persona-test.js          # 전부
node scripts/persona-test.js P1 P6    # 골라서
```

- 데모 DB를 **복사해서** 씁니다. 실제 데이터는 건드리지 않습니다.
- 발견은 던지지 않고 모읍니다. 하나 실패해도 끝까지 갑니다.
- 화면은 `docs/persona/` 에 증거로 남습니다.
- 결과는 `docs/페르소나테스트.md` 로 나옵니다.

## 3회차 — 자동 검사가 못 잡던 것 (테두리 사건)

테두리(고리)가 얼굴을 가로질러 그려지고 있었는데, 페르소나 13명이 **발견 0건**으로
통과했습니다. 배포까지 나가서 사람이 눈으로 보고 지적했습니다. 왜 못 잡았는지:

| | 왜 못 봤나 |
|---|---|
| 단위 테스트 | "고리 태그가 있는가"만 확인 — **크기**는 안 봤다 |
| 흐름 테스트 | 화면은 200 OK, 요소도 제자리. 아무 문제 없음 |
| 대비 검사 | 글자 색만 잰다. 그림끼리 겹치는 건 대상이 아니다 |
| 스크린샷 | **남기기만 하고 아무도 안 열어봤다.** 게다가 그림이 뜨기 전에 찍혀 아바타 자리가 빈 동그라미였다 |

원인도 흔한 종류였습니다. `style.css` 의 `.avatar-ring { width: 132% }` 가
위쪽 `.avatar img { width: 100% }` 에게 **우선순위에서 져서** 통째로 무시됐습니다.
문법 오류가 아니라 조용히 무시되는 종류라 어디에도 흔적이 남지 않습니다.

그래서 세 가지를 넣었습니다.

1. **크기를 CSS 에서 뺐습니다.** 고리·얼굴 크기는 `src/avatars.js` 가 요소에 직접
   붙입니다. 인라인 스타일은 어떤 선택자도 이기지 못해 같은 사고가 다시 안 납니다.
2. **눈으로 보던 것을 숫자로 바꿨습니다.** `test/avatar-ring.test.js` 가 테두리 PNG 9장을
   직접 읽어 구멍 크기를 재고, `구멍 ≥ 얼굴` 인지 확인합니다.
   옛 코드로 되돌려 돌려보면 `구멍이 0.61 인데 얼굴이 1 라 19.5% 씩 겹친다` 로 잡힙니다.
3. **스크린샷이 진실을 담게 했습니다.** 찍기 전에 그림이 다 뜰 때까지 기다리고,
   찍을 때마다 *잘라내는 상자 밖으로 삐져나간 그림*이 있는지 함께 검사합니다.

### 남는 한계 (정직하게)

이 셋으로도 **"되긴 하는데 못생겼다"** 는 못 잡습니다. 간격이 어색하다, 색이 진하다,
글씨가 크다 — 전부 이번에 같이 받은 지적인데 기계가 판정할 수 있는 종류가 아닙니다.
이런 건 **사람이 보거나**, 이전 화면과 비교(visual regression)해서 *달라진 곳*을
사람에게 보여주는 수밖에 없습니다. 지금은 전자로 갑니다.

## 4회차 — 사람 눈으로 화면 훑기

3회차에서 "보기 싫은 것은 사람이 봐야 합니다" 라고 적어 놓고, 실제로 화면을
하나씩 열어 봤습니다. 자동 검사 189개와 페르소나 13명이 전부 통과한 상태에서
**5건**이 나왔습니다.

| 화면 | 무엇이 | 왜 자동 검사가 못 봤나 |
|---|---|---|
| 이벤트·포인트 | 구매 내역이 `+-20,000P` (부호 두 개) | 화면에 글자가 있는지만 봤지 *내용*을 안 봤다 |
| 이벤트·포인트 | "오늘 적립 −21,990P" — 적립인데 음수 | 계산은 맞았다. 라벨과 안 맞는 게 문제였다 |
| 캐릭터 상점 | 테두리 칸에서 '사용 안 함'만 얼굴이 큼 (68px 대 55px) | 둘 다 정상 크기다. 나란히 놓였을 때만 어긋난다 |
| 글 상세 | 댓글 입력 안내가 "…하루 10개까" 에서 잘림 | 글자는 다 있다. 칸보다 길 뿐이다 |
| 마이페이지 | "출석 0일" 인데 포인트 내역엔 출석체크·연속 출석 보너스 | 데모 데이터끼리 앞뒤가 안 맞은 것 |

다섯 건 모두 **한 화면 안에서는 아무 문제가 없고, 다른 것과 나란히 놓고 봐야만
드러나는** 종류입니다. 요소 하나씩 검사하는 방식으로는 원리상 안 걸립니다.

고친 뒤에는 다시 숫자로 바꿔 회귀 검사를 붙였습니다
(부호 2개 · 오늘 적립 1개 · 얼굴 크기 1개).

### 이번에 확인해 보고 '결함 아님' 으로 넘긴 것

- 에디터 툴바가 좁은 화면에서 잘리는 것 — 오른쪽에 흐림 처리로 "더 있다" 를 이미 알리고 있었다
- 캐릭터 25칸에서 보유/잠금이 구분 안 되는 것처럼 보인 것 — 보유한 칸이 스크롤 아래에 있었을 뿐
- 알림 카드가 커 보인 것 — 알림이 한 건뿐이라 그렇게 보였다

## 5회차 — 안 열어 본 화면이 없게 (전 화면 훑기)

4회차까지는 제가 **골라서** 열어 봤습니다. 그러다 보니 회원가입·신고 관리·회원 관리
같은 화면은 한 번도 안 봤고, 화면 폭도 412px 하나만 봤습니다.
그래서 목록을 사람이 아니라 기계가 만들게 했습니다 — `npm run sweep`.

링크를 타고 닿는 모든 화면을 **비로그인 · 여성회원 · 남성회원 · 업소회원 · 운영자**
다섯 사람으로 각각 열어, 한 화면만 보고도 답이 나오는 것들을 잽니다.

| 재는 것 | 왜 |
|---|---|
| 가로 스크롤 | 모바일에서 제일 흔하고 제일 티 난다 |
| 깨진 그림 | 파일 이름이 틀렸거나 없다 |
| 겹치는 id | 라벨·앵커가 엉뚱한 곳을 가리킨다 |
| 누르는 자리 크기 | 기준은 24px (WCAG 2.5.8 AA) |
| 칸 밖으로 잘린 글자 | 말줄임 처리도 없이 잘리는 것 |
| 입력칸 안내문 길이 | 칸보다 길면 잘려서 안내가 안 된다 |
| 세로로 쌓인 버튼 글자 | '등록' 이 '등/록' 으로 접힌 것 |
| 콘솔 오류 · 못 받아온 파일 | 화면엔 안 보이지만 뭔가 깨진 것 |

**300개 화면**(다섯 사람 × 60개)을 네 가지 폭(320 · 412 · 768 · 1280)으로 돌렸습니다.

### 나온 것 (전부 고침)

| 어디 | 무엇이 | 폭 |
|---|---|---|
| 마이페이지 · 남 프로필 | 화면이 가로로 4px 넘침 — `1fr` 은 `minmax(auto,1fr)` 이라 칸이 안 접혔다 | 412 |
| 글 상세 | ⋮ 메뉴가 30×30 | 412 |
| 캐릭터 상점 | 뒤로가기 ← 가 30×33 | 412 |
| 댓글 | '답글' 이 25×17, 좋아요가 22px | 412 |
| 글쓰기 | '? 작성가이드' 가 19px | 412 |
| 캐릭터 상점 | 3열 격자가 33px 넘침 (칸 79px 인데 그림 88px) | 320 |
| **신고 관리** | **제목 자리가 10px 로 찌그러져 글자가 세로로 한 자씩 쌓임** | 320 |
| 댓글 | '등록' 버튼이 '등/록' 으로 접힘 | 320 |
| 댓글 | 안내문이 칸보다 길어 잘림 → 포인트 안내를 칸 밖으로 뺐다 | 320 |

지금은 네 가지 폭 모두 **0건** 입니다.

### 검사기 자신도 틀릴 수 있다

처음 돌렸을 때 231건이 나왔는데 대부분 오탐이었습니다.

- 화면에 안 그리고 읽어 주기만 하는 글(`.sr-only`)은 폭이 1px 이라 늘 '잘림' 으로 잡혔다
- 문장 속 글자 링크(작성자 이름)를 '작은 버튼' 으로 셌다 — 접근성 기준에서도 예외인 것들이다
- 누르는 자리 기준을 44px(AAA 권장)로 잡았더니 멀쩡한 버튼까지 다 걸려 진짜가 묻혔다 → 24px(AA)로 낮췄다
- '세로로 쌓인 버튼' 을 높이로 재려다 *높이를 고정한* 버튼까지 걸렸다 → 글자가 실제로 몇 줄에
  그려졌는지(`Range.getClientRects()`)로 바꿨다

**검사기를 새로 만들면 고친 것을 되돌려 놓고 한 번 돌려 봅니다.** 안 잡히면 그 검사기는
아무것도 지켜 주지 않는 것입니다. ('등록' 버튼도 그렇게 확인했습니다 — 되돌리니 124건.)

## 여섯째 판 — 인수인계 문서가 사람이 쓴 것처럼 읽히는가

`npm run docs`

"AI 가 쓴 것 같지 않게 해 달라" 는 말을 듣고 문서를 다 고쳤는데, 고치고 나서 **나아졌는지
확인할 방법이 없었습니다.** 감으로 고치고 감으로 만족한 셈입니다. 그래서 티가 나는 버릇
몇 가지를 숫자로 재기로 했습니다.

문장 길이가 다 똑같은지, 문단 길이가 다 똑같은지, 굵게 표시와 줄표(—)를 얼마나 썼는지,
쓴 사람 흔적이 있는지를 봅니다.

### 고치기 전과 후

|  | 고치기 전 | 지금 |
|---|---|---|
| 걸린 것 | 15건 | 4건 |
| 굵게 (1000자당) | 5 ~ 19.3 | 0 ~ 0.4 |
| 줄표 — (1000자당) | 최대 3.6 | 0 ~ 1.4 |

### 이 검사가 잡아낸 진짜 문제

처음에 저는 "표를 걷어내고 문장으로 풀면 사람 글 같아진다" 고 생각했습니다. **이게 틀렸습니다.**

표에는 두 종류가 있습니다.

- **찾아보는 표** — 칸이 짧고, 눈이 뛰어서 원하는 줄을 찾습니다. 이건 표가 맞습니다
- **접어 둔 표** — 칸이 길고, 원래 문장인데 표에 욱여넣은 것입니다. 이건 펴야 합니다

저는 둘을 구별하지 않고 다 폈습니다. 그래서 `원본소스/src/routes/board.js` 처럼 앞이
똑같은 경로 네 개가 한 문장에 줄줄이 들어가게 됐습니다. 원래 표였을 때는 눈이 '포인트 규칙'
줄로 바로 뛰었는데, 문장이 되니 다 읽어야 찾습니다. **읽기 나쁘게 만든 것입니다.**

검사기가 이걸 잡아 줘서 되돌렸습니다. 되돌린 곳은 다섯 군데입니다.

| 어디 | 무엇 |
|---|---|

## 일곱째 판 — 화면 PHP 가 진짜로 그려지는가

`php 이식용/test/render.php`

### 왜 만들었나

문서를 아무리 잘 써도 선배님이 하실 일이 줄지 않는다는 걸 뒤늦게 알았습니다.
드리는 게 '함수' 와 '이렇게 생겼습니다 HTML' 두 가지뿐이라, **둘을 잇는 코드는 선배님이
직접 쓰셔야 했습니다.** 그 양을 세어 봤습니다.

| | 줄 수 |
|---|---:|
| 출석체크 마크업 | 482 |
| 캐릭터상점 마크업 | 894 |
| 마이페이지 마크업 | 894 |
| CSS | 1,545 |

3,800줄을 손으로 옮기고 값을 끼우고 POST 를 받는 코드까지 붙이셔야 했습니다. 며칠짜리입니다.
그래서 화면을 PHP 로 만들어 넣기로 했습니다. `이식용/화면/` 이 그것입니다.

이제 선배님이 하실 일은 `include` 한 줄과, 로그인한 사람이 누구인지 알려 주는 함수 하나입니다.

### 화면은 함수와 다르게 확인해야 한다

`run.php` 는 함수만 봅니다. 함수가 다 맞아도 화면은 안 나올 수 있습니다.
그래서 화면 파일을 **진짜로 include 해서** 나온 HTML 을 봅니다.

- HTML 이 나오는가, 오류 문구가 안 섞였는가
- `<div>` `<form>` 여는 것과 닫는 것 수가 같은가
- 버튼을 눌렀을 때 값이 실제로 바뀌는가 (출석 0일 → 1일, 포인트 차감)
- 폼 위조 막는 값 없이 누르면 **아무 일도 안 일어나는가**
- 로그인 안 한 사람에게 **남의 정보가 안 새는가**

43가지입니다. 화면 세 개를 브라우저로 열어 폭 412px 에서 가로 넘침 0px,
CSS 가 실제로 먹는지(`--primary` 가 잡히는지), 그림 29장이 다 뜨는지도 확인했습니다.

### 만들자마자 진짜 버그를 잡았다

첫 실행에서 상점 화면이 통째로 죽었습니다.

```
Cannot redeclare function cm_shop_url()
```

도우미 함수를 화면 파일 안에 뒀는데, 한 요청에서 그 파일을 두 번 include 하면 페이지가
통째로 죽습니다. 기존 사이트에 붙이시다 보면 충분히 있을 수 있는 일입니다.
`cm_ui.php`(require_once 로 한 번만 읽는 파일)로 옮겨서 고쳤습니다.

**이건 문서를 아무리 읽어도 안 나오는 종류의 버그입니다.** 돌려 봐야 나옵니다.

### CSS 를 남의 사이트에 쏟지 않기

우리 `style.css` 에는 `body`, `*`, `.card` 같은 흔한 이름이 그대로 있습니다.
이대로 올리면 **기존 사이트 화면까지 같이 바뀝니다.** 남의 사이트를 망가뜨리는 것입니다.

`scripts/make-port-css.js` 가 선택자마다 앞에 `.cm` 을 붙여 `<div class="cm">` 안에서만
듣게 만듭니다. 규칙 725개를 가뒀고, 못 가둔 선택자가 하나라도 남으면 오류를 내고 멈춥니다.

여기서도 한 번 틀렸습니다. 주석 앞의 줄바꿈을 흘려버려서 `.cm { /* 주석` 처럼 붙어 나왔습니다.
모양만 상하는 것이라 안 고쳐도 됐지만, 선배님이 읽으실 파일이라 고쳤습니다.

## 여덟째 판 — 고리 밖으로 얼굴이 새던 것

`node --test test/avatar-ring.test.js`

### 지적받은 것

상점 화면을 72px 로 크게 놓고 보니 캐릭터의 머리와 어깨가 **고리 밖으로 삐져나와** 있었습니다.

먼저 이식하면서 생긴 것인지부터 봤습니다. Node 와 PHP 를 나란히 그려 재 보니
얼굴 66.2px · 고리 86.4px · 중심 좌표까지 **완전히 같았습니다.**
이식 문제가 아니라 원래 설정이 그랬던 것입니다.

### 왜 검사를 통과했나

고리 그림 9개 × 각도 360개, 3,239개 표본으로 바깥선 반지름을 쟀습니다.

| | 그림 크기 대비 |
|---|---:|
| 가장 안쪽 | 0.667 |
| 하위 1% | 0.698 |
| 가운뎃값 | 0.802 |
| 가장 바깥 | 0.948 |

고리는 붓으로 휘갈긴 모양이라 바깥선이 **0.67 에서 0.95 까지 출렁입니다.**

`RING 1.20` 은 가운뎃값(0.816)에 맞춘 값이었습니다. "고리 바깥이 칸을 꽉 채운다" 는 규칙으로요.
그런데 가는 쪽에서는 바깥선이 칸의 1.20 × 0.691 = **0.83** 밖에 안 되는데
얼굴이 **0.92** 라, 그 각도에서 얼굴이 4.1%p 만큼 밖으로 나왔습니다.

**검사가 `edge`(가운뎃값)와 `edgeMax`(최댓값)만 보고 최솟값은 안 봤습니다.**
그래서 눈에 보이는 결함이 검사를 통과했습니다. 이 파일에 이미 같은 실수가 한 번 적혀 있습니다.
"처음에는 mid 만 보고 기준을 세웠는데, 그래서 얼굴 가장자리를 고리가 무는 상태가 통과했다."
**안쪽 경계에서 배운 걸 바깥 경계에 적용하지 않았습니다.**

### 고친 것

규칙을 바꿨습니다.

- 전: 고리 바깥(**가운뎃값**)이 칸을 꽉 채운다 → RING = 1/0.816 = 1.20
- 후: 고리가 **가장 가는 쪽** 바깥선이 얼굴보다 밖에 있다 → RING ≥ 0.92/0.691 = 1.34

얼굴 92% 는 눈으로 직접 고르신 값이라 건드리지 않고 고리만 키웠습니다.

대신 가장 굵은 쪽은 칸을 넘습니다 (1.34 × 0.95 = 1.27). 넘는 것 자체는 괜찮습니다.
목록 아바타는 44px 이고 글 제목까지 간격이 16px 인데 한쪽으로 나가는 건 6px 뿐입니다.
칸 넘침 한도를 1.20 에서 1.36(간격의 절반)으로 올리면서 그 계산을 주석에 적어 뒀습니다.

### 새로 넣은 검사

`얼굴이 고리 바깥으로 삐져나오지 않는다` — 각 고리의 바깥선 **최솟값**을 재서
`FACE <= RING × edgeMin` 인지 봅니다.

되돌려서 확인했습니다. RING 1.20 으로 두면
`border-cyan: 고리가 가장 가는 쪽 바깥선이 칸의 83% 인데 얼굴이 92% 라 그만큼 밖으로 나온다`
로 걸리고, 1.34 로 올리면 통과합니다.

### 다시 확인한 것

- 전 화면 훑기 300개 · 0건 (고리를 키웠는데도 옆 글자를 안 밉니다)
- `npm run ring` 실측: 몸통 0.854~1.000, 얼굴 0.916 — 몸통의 42% 지점
- PHP 화면 43가지 · 상점 가로 넘침 0px

## 아홉째 판 — 전체 검토

"다른 부분들도 싹 검토해 봐" 라는 말을 듣고 훑었습니다. 세 가지가 나왔습니다.

### 1. 손으로 만든 것은 반드시 낡는다

고리 크기를 1.20 에서 1.34 로 고쳤는데, 선배님이 마크업 참고하실
`이식용/화면HTML/` 26군데가 옛 값 그대로였습니다. **거기서 복사해 쓰시면 방금 고친 게
도로 들어갑니다.** 이 폴더를 손으로 뽑아 뒀던 게 원인입니다.

같은 이유로 `이식용/원본소스/` 에도 새로 만든 파일 세 개가 빠져 있었습니다.

둘 다 스크립트로 바꾸고, 낡았는지 보는 방법을 붙였습니다.

| | 다시 만들기 | 낡았는지 보기 |
|---|---|---|
| 화면HTML | `npm run screens` | `node scripts/make-screens.js --check` |
| 원본소스 | `npm run portsrc` | `node scripts/make-port-src.js --check` |

`npm run port` 하나로 이식 꾸러미 전체를 봅니다.

되돌려서 확인했습니다. 목록.html 을 옛 값으로 되돌리니
`화면HTML 이 지금 코드와 다릅니다 (1개): 목록` 으로 걸립니다.

### 2. 잔액은 안 빠졌는데 구매 기록만 남을 수 있었다

`cm_spend()` 는 이렇게 되어 있었습니다.

```sql
UPDATE users SET points = points - ? WHERE id = ? AND points >= ?
```

`AND points >= ?` 로 막아 둔 건 맞는데, **몇 줄이 바뀌었는지를 안 봤습니다.**
UPDATE 는 한 줄도 못 바꿔도 '성공' 으로 돌아옵니다. 직접 재 봤습니다.

```
잔액 0 인데 2000 을 빼는 UPDATE
  바뀐 줄 수 : 0
  cm_q 결과  : true — 성공했다고 돌려줍니다
```

두 요청이 겹치면 (버튼을 빨리 두 번 누르는 것으로 충분합니다) 둘 다 잔액을 읽고 통과한 뒤,
뒤쪽 UPDATE 만 빈손으로 끝납니다. 그런데 그냥 commit 해 버리니
**포인트는 한 번만 빠졌는데 구매 기록은 두 번 남습니다.** 오류가 안 나서 아무도 모릅니다.

`cm_affected()` 를 만들어 실제로 바뀐 줄 수까지 보게 고쳤습니다.
`cm_buy()` 도 순서를 바꿨습니다 — 보유 목록에 먼저 넣고(UNIQUE 가 겹침을 막습니다)
돈을 뺀 뒤, 돈 빼기가 실패하면 넣었던 것을 도로 뺍니다.

지금 돌고 있는 Node 쪽은 괜찮았습니다. `user_items` 에 UNIQUE 가 걸려 있고
`db.transaction()` 안에서 터져 통째로 롤백됩니다.

#### 검사를 만드는 게 더 어려웠다

처음 만든 검사는 못 잡았습니다. `cm_spend` 가 자기 안에서 잔액을 먼저 읽어서
0원이면 UPDATE 까지 가지도 않기 때문입니다. **읽기와 UPDATE 사이에 남이 끼어든 상황**을
만들어야 하는데 한 프로세스에서는 그 틈이 안 생깁니다.

내역이 들어가는 순간 잔액을 0으로 만드는 트리거를 걸어 흉내 냈습니다.
`cm_spend` 입장에서는 남이 끼어든 것과 똑같습니다.

되돌려서 확인했습니다. 고침을 빼면
`읽은 뒤에 남이 먼저 빼 가면 실패로 끝난다 (true)` 와
`그때 구매 내역이 남지 않는다 (12 (전 11))` 가 걸립니다.

### 3. 회원번호 자동 찾기가 너무 헐거웠다

`cm_current_user_id()` 가 `$_SESSION['no']` `['idx']` `['uid']` 까지 봤습니다.
기존 사이트가 거기에 **페이지 번호나 게시판 번호**를 담아 뒀으면 그 값을 회원번호로 씁니다.
엉뚱한 사람에게 포인트가 붙는데 오류가 안 납니다.

회원을 가리키는 게 분명한 이름만 남겼습니다. 못 찾으면 0 을 주고 화면이 안내를 띄웁니다.
`$CM['debug']` 를 켜면 지금 세션에 어떤 이름들이 있는지도 보여 줍니다
(붙이시는 동안만 켜고 끄시라고 적어 뒀습니다).

### 어긋나면 바로 알게 만든 것

`test/port-parity.test.js` — 드리는 PHP 가 지금 프로그램과 같은 규칙인지 봅니다.
포인트 금액·하루 한도 13가지, 연속 보너스 날짜, 캐릭터·테두리 값,
**고리와 얼굴 크기**, 캐릭터 246종 목록.

이번에 고리 크기가 어긋났던 게 바로 이 종류입니다. Node 만 고치고 PHP 를 안 고치면
선배님 사이트에서만 캐릭터가 삐져나옵니다. 이제 `npm test` 에서 걸립니다.

### 깨끗했던 것

- 화면 PHP 세 개에 이스케이프 없이 내보내는 값 없음 (걸린 7군데는 전부 우리가 만든 숫자·고정 문자)

전체 목록에서 2번째 글(질문, 31번)을 눌러 보니 이랬습니다.

| | |
|---|---|
| 전체 목록에서 바로 위 | 32번 (이벤트) |
| 전체 목록에서 바로 아래 | 30번 (자유) |
| 실제 이전글 | **24번** |

같은 질문 말머리만 훑느라 목록에서 옆에 있던 글을 건너뛰었습니다.
화면에는 오류가 없고 링크도 멀쩡해서, 눌러 보기 전에는 모릅니다.

주소에 말머리가 없으면 전체로 보게 고쳤습니다.

### 넣은 검사

`test/flows.test.js` — 자유·질문을 번갈아 넣고 공지도 하나 끼운 뒤,

- 전체에서 들어오면 말머리와 상관없이 목록의 윗줄·아랫줄
- 자유 탭에서 들어오면 자유끼리
- 질문 탭에서 들어오면 질문끼리
- 어느 쪽에서도 공지는 안 끼어든다

되돌려서 확인했습니다. 탭 정보가 없을 때 그 글의 말머리로 가두면
`전체에서 들어오면 말머리와 상관없이 목록의 윗줄·아랫줄이어야 한다` 로 걸립니다.

### 검색과 정렬까지 따라가게 (이어서)

처음에는 말머리까지만 하고 검색어·정렬은 뒀는데, 그것도 따라가게 해 달라고 하셔서 마저 했습니다.

**조건을 두 군데 적으면 반드시 어긋납니다.** 목록은 검색을 고쳤는데 이전글·다음글은 안 고치면
'목록에는 있는데 다음글로는 안 넘어가는 글' 이 생깁니다. 오류가 안 나서 알기도 어렵습니다.
그래서 목록을 거르는 조건을 `listFilter()` 한 곳으로 빼고 양쪽이 같은 것을 쓰게 했습니다.

정렬이 붙으면 한 칸 움직이는 게 번호 비교만으로는 안 됩니다. 추천 수가 같은 글이 수두룩해서
번호까지 같이 봐야 합니다.

```
아래로 (이전글) : (추천, 번호) 가 지금 것보다 작은 것 중 제일 큰 것
위로   (다음글) : (추천, 번호) 가 지금 것보다 큰 것 중 제일 작은 것
```

브라우저로 다섯 조합을 목록 순서와 맞춰 봤습니다.

| 조건 | 결과 |
|---|---|
| 전체 · 최신순 | 목록과 같음 |
| 자유 탭 | 목록과 같음 |
| 검색 "알바" | 목록과 같음 |
| 조회순 | 목록과 같음 |
| 검색 "알바" + 조회순 | 목록과 같음 |

검사도 넣었습니다. 검색어가 든 글 셋 사이에 안 든 글 둘을 끼워 놓고,
검색해서 들어오면 낀 글을 건너뛰는지, 추천순·조회순이면 그 차례로 이어지는지 봅니다.

되돌려서 확인했습니다. 이전글·다음글이 말머리만 보게 되돌리면
`검색해서 들어오면 검색 결과 안에서만 이어져야 한다` 로 걸립니다.

## 열두째 판 — 랭킹 안내문을 고치려다 진짜 버그를 찾음

랭킹에서 남성·업소 회원과 운영자를 뺐는데 안내문이 "회원 TOP 20" 그대로라 오해할 수 있어서
"여성회원 TOP 20" 으로 고치려던 참이었습니다. 글자만 바꾸면 되는 일인 줄 알았는데,
**남의 프로필에 찍히는 '랭킹 N위' 는 안 고쳐져 있었습니다.**

숫자를 나란히 놓고 보니 이랬습니다.

| | 랭킹 목록 | 프로필 |
|---|---|---|
| 골드웨이브 | 1위 | **2위** |
| 민트소다 | 2위 | 3위 |
| 체리블라썸 | 4위 | **7위** |
| 운영자 | 없음 | **1위** |
| 나이트캣 (남성) | 없음 | **6위** |
| 루노라운지 (업소) | 없음 | **5위** |

프로필 쪽은 전체 회원을 세고 있어서, 랭킹 1위인 사람 프로필에 2위라고 적히고
랭킹에 없는 사람한테도 등수가 찍혔습니다.

조건을 `RANK_WHERE` 한 곳으로 빼고 양쪽이 같은 것을 쓰게 했습니다.
자격이 없는 사람에게는 순위를 아예 안 보여 줍니다.
(목록에 없는데 등수만 있으면 더 이상합니다)

### 고치고 나서 또 틀렸습니다

고쳤더니 이번엔 **아무한테도 순위가 안 나왔습니다.** 프로필 쿼리가 `member_type` 을
안 뽑아 오고 있어서 `undefined === 'female'` 이 되어 전원이 자격 없음으로 걸렸습니다.
`SELECT` 에 칸 하나를 더해 고쳤습니다.

코드만 봤으면 못 찾았을 것입니다. 화면에 찍힌 숫자를 목록과 나란히 놓고 봐서 나왔습니다.

### 검사를 만들 때도 틀렸습니다

처음 만든 검사는 '목록에 없으면 순위도 없어야 한다' 로 썼습니다.
그런데 목록은 **TOP 20 까지만** 보여 줍니다. 55위인 사람은 목록에 없어도 순위는 있어야
맞습니다. '자격이 있는가' 와 '상위 20위 안인가' 를 갈라서 다시 썼습니다.

- 목록에 나오는 사람은 전부 자격이 있는 사람인가
- 자격 있는 사람 중 포인트 1등이 목록 1위인가
- 목록에 든 사람의 프로필 순위가 목록 위치와 같은가
- 20위 밖인 사람은 순위가 있되 20보다 뒤인가
- 자격 없는 사람은 순위가 아예 안 나오는가

되돌려서 둘 다 확인했습니다.

```
① 프로필 순위를 전체 회원 기준으로 → 운영자: 랭킹 자격이 없는데 프로필에 2위라고 적힌다
② member_type 을 빼면            → 체리블라썸: 목록 8위인데 프로필은 순위 없음
```

## 열셋째 판 — 베스트댓글을 다시 넣음 (같은 실수 안 하게)

"댓글 베스트가 다시 있으면 좋겠다, 좋아요 4개 이하는 지정 안 되게" 라고 하셔서 되살렸습니다.

### 왜 뺐었나부터 봤습니다

기록을 보니 두 번 손댄 자리였습니다. 처음에는 추천 많은 댓글을 맨 위에 **복사해서**
보여 줬는데, 수정사항 11번으로 베스트 뱃지를 떼자 **같은 댓글이 아무 표시 없이 위아래로
두 번** 나오게 됐습니다. 그래서 복사본을 아예 없앴었습니다.

그대로 되돌리면 그 문제가 그대로 돌아옵니다. 그래서 방식을 바꿨습니다.

| | 예전 | 지금 |
|---|---|---|
| 방식 | 맨 위에 **복사** | 원래 자리에서 **빼서 옮김** |
| 같은 댓글이 | 두 번 나옴 | 한 번만 나옴 |
| 기준 | 좋아요 3개 | 좋아요 **5개** |
| 개수 | 상위 2개 | 상위 2개 (같음) |
| 답글 | 같이 올라감 | 안 올림 |

답글을 안 올리는 이유는, 부모와 떨어지면 무슨 말인지 알 수 없어지기 때문입니다.

### 검사

- 좋아요 5개는 베스트, **4개는 아니다** (경계를 딱 짚습니다)
- 같은 댓글이 **한 번만** 나온다 — 예전에 지적받은 그것
- 베스트가 맨 위에 있다
- 답글은 안 올라간다

되돌려서 셋 다 확인했습니다.

```
기준을 4로 낮추면          → 좋아요 5개부터 베스트, 4개는 안 된다  실패
옛날처럼 복사해서 붙이면    → 좋아요 5개부터 베스트, 4개는 안 된다  실패 (복사본 검사에 걸림)
답글도 베스트로 올리면      → 답글은 베스트로 떼어 올리지 않는다    실패
```

### 데모 데이터도 경계가 보이게

같은 글에 좋아요 5개짜리와 4개짜리를 나란히 뒀습니다. 화면을 열면 5개짜리만 위로
올라가 있어서, 기준이 어디인지 눈으로 바로 보입니다.

넣다가 한 번 터졌습니다. 아래에 이미 같은 댓글에 좋아요를 넣는 줄이 따로 있어서
`UNIQUE constraint failed` 로 서버가 안 떴습니다. 한 줄로 합쳐 고쳤습니다.

### "원래 4개 아니었나" 를 확인했습니다

다시 넣고 나서 "원래 4개면 올라가지 않았냐" 는 말씀이 있었습니다. 저는 README 만 보고
"3개였습니다" 라고 답했는데, git 기록에서 첫 코드를 꺼내 보니 이랬습니다.

```js
// 베스트댓글: 좋아요 3개 이상인 최상위 댓글 중 상위 2개 (에브리타임식)
const best = rows.filter((c) => !c.parent_id && c.like_count >= 3)
  .sort((a, b) => b.like_count - a.like_count || a.id - b.id)
  .slice(0, 2);
```

기준은 3개가 맞는데, **그때 화면에 베스트로 보이던 댓글이 좋아요 4개짜리**였습니다
(데모 데이터가 4개였습니다). 그래서 "4개면 올라갔다" 는 기억이 맞는 것이었습니다.

그리고 **제가 놓친 것이 하나 더 나왔습니다.** 원래는 `.slice(0, 2)` 로 상위 2개까지만
올렸는데, 다시 넣을 때 기준만 넘으면 전부 올리게 만들어 뒀습니다. 댓글이 많은 글에서는
절반이 '베스트' 가 되어 뱃지가 뜻을 잃습니다. 원래대로 되돌리고 검사를 넣었습니다.

기준을 넘는 댓글 넷(좋아요 8·7·6·5)을 놓고 둘만 올라가는지 봅니다.
제한을 빼면 `기준을 넘은 댓글이 4개인데 베스트가 4개다` 로 걸립니다.

**기억이 코드보다 정확할 때가 있습니다.** README 만 보고 답하지 말았어야 했습니다.

## 열넷째 판 — 닉네임으로도 검색되게

"검색에서 닉네임으로도 검색되게 해 달라" 는 요청입니다.

### 익명 글이 새면 안 됩니다

조건 한 줄 더 붙이는 일인 줄 알았는데, 붙이자마자 걸리는 게 있었습니다.
**닉네임으로 검색해서 그 사람 익명 글이 나오면 익명이 아니게 됩니다.**
화면에는 '익명' 이라고 적혀 있어도 검색으로 누가 썼는지 드러납니다.

그래서 닉네임 조건에는 `p.is_anonymous = 0` 을 반드시 같이 겁니다.
제목·본문 검색은 그대로라, 익명 글도 제목으로는 찾아집니다 (그건 누가 썼는지 안 드러납니다).

### 느려지는 걸 재서 방식을 바꿨습니다

처음에는 조건 안에서 users 를 `EXISTS` 로 뒤졌습니다. 돌려 보니 느렸습니다.
`OR` 가 붙으면 SQLite 가 제목·본문 색인을 못 쓰고 글 표를 통째로 훑습니다.

글 2만 건으로 재 봤습니다.

| 검색 | 닉네임 넣기 전 | EXISTS 방식 | 지금 방식 |
|---|---:|---:|---:|
| 결과 없음 | 0.1ms | 7.3ms | **0.1ms** |
| 닉네임 1명 걸림 | 0.1ms | 7.5ms | 4.5ms |
| 흔한 낱말 (2만 건 매칭) | 4.3ms | 4.4ms | 4.4ms |

닉네임이 걸리는 사람을 **먼저** 찾아 두고 `user_id IN (...)` 으로 잇는 방식으로 바꿨습니다.
회원 표는 글 표보다 훨씬 작아서 이쪽이 싸고, `posts(user_id)` 에 인덱스도 이미 있습니다.
**걸리는 사람이 없으면 그 줄이 아예 사라져서** 예전과 똑같은 속도로 돕니다.
평소 검색은 대개 이 경우라 사실상 느려지지 않았습니다.

닉네임이 진짜로 걸릴 때만 4.5ms 인데, 그건 사람 이름을 일부러 친 경우라 괜찮다고 봤습니다.

### 검사

- 닉네임으로 검색하면 그 사람 글이 나온다
- **익명 글은 안 나온다**
- 닉네임 일부만 쳐도 찾아진다
- 제목 검색은 익명 글도 나온다 (그건 안 드러나니까)

되돌려서 둘 다 확인했습니다.

```
닉네임 조건을 빼면   → 닉네임으로 검색하면 그 사람 글이 나온다  실패
익명 제외를 빼면     → 익명 글이 닉네임 검색에 걸리면 안 된다   실패
```

## 열다섯째 판 — 베스트댓글 테두리, 그리고 이식용 CSS 가 낡아 있던 것

하늘 님이 "베스트 댓글 테두리 있던 전 버전으로" 라고 하셨습니다.
"테두리 있지 않았나" 하셔서 찾아봤더니 **있었습니다.**

```css
}
```

이걸 열셋째 판에서 다시 넣을 때 배경만 넣고 테두리를 빠뜨렸습니다.
`--trending-bg` · `--trending-line` 두 색이 **아무 데서도 안 쓰이는 채로** 남아 있던 게
그 증거였습니다. 원래 이 규칙 전용으로 만든 색인데 규칙만 사라졌던 것입니다.

### 잰 값

CSS 파일에 그렇게 적혀 있다고 그렇게 그려지는 게 아닙니다.
전에 캐릭터 고리가 딱 그래서 통째로 무시된 적이 있어서, 이번에는 화면에서 쟀습니다.

|---|---|---|
| 테두리 | 1px solid #ffe0cc | 1px solid #4a3a2b |
| 배경 | #fff5ee | #2a231d |
| 네 면 다 있나 | 예 | 예 |
| 맨 위에 있나 | 예 (0번째) | 예 (0번째) |

### 되돌려서 확인

전 화면 훑기에 검사를 붙였습니다. `.comment.best` 에 **보이는 테두리가 있는지**
—- 굵기가 0 이 아닌지, 배경과 같은 색은 아닌지, 투명하지 않은지 — 를 봅니다.

```
테두리를 빼면  → 화면 300개 · 발견 11건  (다섯 사람 화면 전부에서)
테두리를 넣으면 → 화면 300개 · 발견 0건
```

### 하다가 나온 것 ① — 규칙이 두 군데 박혀 있었다

열셋째 판에서 넣을 때 `.badge-free` 를 기준으로 끼워 넣었는데,
`.badge-free` 가 파일에 두 번 있어서 **양쪽에 다 들어갔습니다.** 하나로 줄였습니다.

### 하다가 나온 것 ② — `.comment:last-of-type` 은 아무것도 안 고른다

"이 줄을 위로 옮기면 이러이러해서 위험하다" 고 주석에 쓰려다가,
정말 그런지 재 봤더니 **아니었습니다.**

`:last-of-type` 은 class 가 아니라 **태그 이름**으로 셉니다.
댓글 뒤에는 항상 `div.empty` 나 댓글 입력칸이 따라오기 때문에,
마지막 댓글은 형제 `div` 중 마지막이 아닙니다.

```
.comment 개수                    3
.comment:last-of-type 에 걸린 것  0      ← 하나도 없다
마지막 댓글 아래선                1px    ← 지워질 예정이었는데 그대로 있다
```

지금 안 고치고 적어만 둡니다. 지우면 **마지막 댓글 밑 회색 줄이 없어지는**
눈에 보이는 변화라, 하늘 님이 정하실 일입니다.

### 하다가 나온 것 ③ — 이게 제일 큽니다

`이식용/화면HTML/css/style.css` 는 **아무 스크립트도 안 만드는 파일**이었습니다.
처음에 손으로 한 번 복사해 두고 잊었습니다.

그래서 열셋째 판에서 베스트댓글 모양을 넣었을 때 이 사본에는 안 들어갔고,
`cm.css` 를 **이 사본에서 만들기 때문에** 선배님이 실제로 쓰시는 CSS 에도 안 들어갔습니다.
우리 화면에서만 멀쩡했습니다.

`make-screens.js` 가 이 파일도 같이 복사하고, `--check` 로 낡았는지도 보게 했습니다.

```
사본을 낡게 만들고 → 종료코드 1  "화면HTML 이 지금 코드와 다릅니다 (1개): css/style.css"
다시 만들고        → 종료코드 0  "화면 13개 · 지금 코드와 같습니다"
```

`npm run port` 순서도 바꿨습니다. 전에는 cm.css 를 **먼저** 만들고 사본 검사를 나중에 했습니다.
사본이 낡았으면 낡은 cm.css 를 이미 써 놓은 뒤에 검사가 실패했습니다. 검사를 앞으로 옮겼습니다.
